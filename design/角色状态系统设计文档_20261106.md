# 角色状态系统设计文档

> 版本：v1.0（设计定稿）
> 日期：2026-11-06（设计）／2026-11-14（最近一次实现核对）
> 状态：**设计已确认并已实现**。三轴数值、生活时间轴、按需视频消费均已落地；默认值 `DEFAULT_ENERGY = 80.0`、心情 50、欲望 30 与本文一致。
> 涉及：精力 / 心情 / 欲望 三条数值 + 生活时间轴 + 视频消费（按需实时刷）+ 群聊三档

---

## 0. 这份文档要解决什么

我想要"群友那套数值系统"（精力条、体力条、欲望值之类），并在此过程中确认了四个真实痛点：

| # | 痛点 | 本设计的回答 |
|---|---|---|
| 1 | 角色话多，连发相似内容，没分寸 | 群聊三档 + 发言节制演出指令 |
| 2 | 刷 B 站太频繁，往心事里塞，触发过多 | 视频消费按需实时刷（2026-11-09 取消视频池）+ 分享带标题链接 |
| 3 | 角色"没在过日子"，叫她才动 | 生活时间轴（她自己编的日子） |
| 4 | 判断项越加越多，怕拖垮回复质量 | **异步判断器**（主回复零负担） |

**设计第一原则：主回复链路必须保持纯净。** 一切数值判断走异步，绝不内联进主回复提示词。

## 1. 总览架构

```
┌────────────────────────────────────────────────────────┐
│                   主回复链路（快，纯净）                 │
│  人设（不限） + 对话上下文 + 演出指令（≤120字）           │
│  → 输出回复                                             │
└────────────────────────────────────────────────────────┘
                          ↓ 回复发出后（异步，不阻塞）
┌────────────────────────────────────────────────────────┐
│                异步判断器（便宜，专心）                  │
│  角色速写(150字) + 当前三值 + 对话片段 + 判断任务         │
│  → {"energy":-1,"mood":+2,"desire":+4,"reason":"..."}  │
└────────────────────────────────────────────────────────┘
                          ↓
┌────────────────────────────────────────────────────────┐
│                  数值引擎（纯计算）                      │
│  应用变化 + 时间回归（心情→50）+ 时间累积（欲望↑）        │
└────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────┐
│              生活时间轴（独立，过去时）                   │
│  事件触发写入 + 空档提醒补写（她自己决定补不补）           │
│  她说"想看点东西"时 → 实时搜视频刷 → 写回时间轴 + 进心事   │
└────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────┐
│              视频消费（按需实时刷，零定时器）             │
│  触发三事件 → 当下实时搜索 → 转写消化 → 挑 1~2 个        │
│  （2026-11-09 取消视频池：池子会过期，实时刷才不尴尬）     │
└────────────────────────────────────────────────────────┘
```

**三条线解耦：**
- 主回复 ↔ 数值：只读演出指令，不写
- 数值 ↔ 时间轴：数值是时间轴的输入（心情低→写低落的日子），不反向
- 时间轴 ↔ 视频：时间轴触发消费，视频按需实时刷（无池子供料）

## 2. 三条数值定义

### 2.1 通用规则

| 项目 | 规则 |
|---|---|
| 存储归属 | `persona_id`（角色卡），角色A/角色B/角色C各自独立 |
| 例外 | **欲望**额外按 `persona_id × owner_qq`（只对我） |
| 范围 | 0~100 浮点，保留 1 位小数 |
| 精度 | 落库 1 位小数 |
| 缺失默认值 | 精力 80、心情 50、欲望 30 |

### 2.2 精力（合并了原"体力条"）

| 项目 | 内容 |
|---|---|
| 含义 | 角色还有多少"力气"做需要消耗的事 |
| 范围 | 0~100 |
| 默认 | 80 |
| 归属 | `persona_id` |

**变化来源：**

**⚠️ 重要原则（我 2026-11-06 拍板）：不做硬编码消耗表，由大模型按时间轴自行判断。**

原因是"累"是拟人概念，不是 AI 概念：

| 错误视角（AI） | 正确视角（拟人） |
|---|---|
| 查文件 -5 | 看一眼而已，不累 |
| 长分析 -5 | 不动体力 |
| — | **出门一趟** -6 ~ -10 |
| — | **打扫/家务** -4 ~ -6 |
| — | **运动/走很久** -8 ~ -12 |
| — | **熬夜** -5/小时 |
| — | **长时间精神投入**（聊很久/情绪激烈）-2/小时 |
| — | 躺着/看书/刷视频 → 几乎不掉 |

**精力 = 体力（含精神头）**，只被"身体/精神真的在动"的事消耗。

**恢复通道（三条，不只靠睡觉）：**

| 通道 | 量级 | 说明 |
|---|---|---|
| 睡觉 | 大幅，×3 加速 | 主力。22:00-08:00 |
| **娱乐回血**（玩游戏、做喜欢的事） | +1 ~ +4 | 主动投入且有正反馈 |
| 闲适回血（发呆、听歌、躺着） | +0.5 ~ +1 | 几乎忽略，但不为负 |
| 刷视频 | 挑中喜欢的 +1~+2；无脑刷 -0.5 | 被动接收，不一定回血 |

**边际递减**：精力 > 80 时，娱乐回血效果减半。避免"靠玩顶满"，睡觉仍是主力恢复。

**恢复公式（向 100 回归，作为兜底机制）：**

```
每小时恢复 = (100 - 当前值) × R_ENERGY
R_ENERGY = 1 - 0.5^(1/16)  ≈ 0.0424
```

含义：16 小时走完到满的一半距离（睡眠期间按 ×3 加速）。

**判断时机（关键）：精力不逐条消息判断，改为「时间轴写入时」判断。**
依据是"她这段时间干了什么"，与聊天解耦。

### 2.3 心情（取代现有"临时情绪"）

| 项目 | 内容 |
|---|---|
| 含义 | 角色此刻开不开心，影响语气和表现 |
| 范围 | 0~100 |
| 默认 | 50 |
| 归属 | `persona_id` |

**变化来源：**

| 来源 | 变化量 | 说明 |
|---|---|---|
| 被夸 / 被关心 | +1 ~ +5 | 异步判断给 |
| 被冷落 / 被骂 | -1 ~ -5 | 异步判断给 |
| 聊得开心 | +1 ~ +3 | 异步判断给 |
| 角色自己调 | ±3 以内 | 允许，但需给理由 |
| 时间回归 | 见公式 | **向 50 收敛** |

**回归公式（关键：越高掉越快，越低涨越快）：**

```
每小时变化 = (50 - 当前值) × R_MOOD
R_MOOD = 1 - 0.5^(1/12)  ≈ 0.0561
```

**示例：**

| 当前 | 6 小时后 | 12 小时后 |
|---|---|---|
| 95 | 78.7 | 70.0 |
| 70 | 63.0 | 58.0 |
| 50 | 50.0 | 50.0 |
| 20 | 30.4 | 34.6 |
| 5 | 15.2 | 17.8 |

**12 小时走完一半距离**，不会一直顶满，也不会一直趴底。

**取代的旧机制：**
- 现有 `affection_hint`（"【心情提示】"那段临时算的提示）**废弃**
- 现有 `set_mood` 工具仍然保留，但它改的是**好感度**（affection，对某人的态度），与心情值不冲突
- 好感度：**对人**（角色A对我 vs 对路人）
- 心情值：**对己**（角色A此刻开心不开心）
- 两者取其一注入提示词时，用不同标签区分

### 2.4 欲望（性欲，只对我）

| 项目 | 内容 |
|---|---|
| 含义 | 角色对我的渴求程度，驱动私密互动 |
| 范围 | 0~100 |
| 默认 | 30 |
| 归属 | `persona_id × owner_qq`（**其他人完全没有这个数值**） |
| 适用场景 | **仅私聊**；群聊彻底屏蔽 |

**变化规律（与心情相反）：**

| 来源 | 变化 | 说明 |
|---|---|---|
| 时间自然累积 | **+2/小时** | 越不管越渴求（放着的欲望上涨） |
| 亲密/暧昧对话 | +1 ~ +8 | 异步判断给，按对话强度 |
| 文爱过程 | -5 ~ -15 | 过程中消耗 |
| 满足后释放 | **-60**（掉到约 40） | 一次满足管一天多 |
| 冷落（长期不互动） | 自然累积的影响 | 不额外处理 |

**累积公式：**

```
每小时累积 = +2.0（线性，不封顶）
上限 clamp 到 100
```

约 **2 天**从 0 涨到 100，约 **1.5 天**涨到"很想"（70）。与我提到的"健康频率约 1.5 天一次"吻合。

**表现随值连续变化（不是硬档位）：**

| 区间 | 连续描述模板（注入提示词） |
|---|---|
| 0~20 | 心很静，没往那方面想 |
| 20~40 | 心里有点软，但还好，不会主动提 |
| 40~60 | 有点想，会不自觉地蹭近一点 |
| 60~75 | 挺想的，话里会带点暗示，想被抱 |
| 75~90 | 忍不住了，会主动贴过来、会催 |
| 90~100 | 几乎克制不住，表现最放开，会主动夜袭 |

**硬开关（护栏）：**

- `desire >= 70` **且** 私聊 **且** 对方是我 → 允许"文爱档"（可连发、主动夜袭）
- 其他任何情况 → **禁止**任何性相关表达

### 2.5 数值总表

| 数值 | 归属键 | 默认 | 回归目标 | 速度 |
|---|---|---|---|---|
| 精力 | persona_id | 80 | 100（满） | 16h 半程 |
| 心情 | persona_id | 50 | 50（中位） | 12h 半程 |
| 欲望 | persona_id × owner_qq | 30 | **无回归，只会涨** | +2/h，满足-60 |

**三种动力学，互不相同：**
- 精力：**耗散型**（用掉就少，休息回来）
- 心情：**回归型**（偏离中位会自动拉回）
- 欲望：**蓄水型**（放着就涨，释放才降）

## 3. 异步判断器

### 3.1 为什么异步（设计理由）

我明确指出：判断项越来越多会拖垮回复质量。本设计用**双链路分离**解决：

| | 主回复 | 异步判断 |
|---|---|---|
| 任务 | 演好角色，回话 | 只判断数值变化 |
| 提示词 | 人设 + 对话 + 演出指令 | 角色速写 + 对话片段 + 判断任务 |
| 干扰 | 零（不知道有数值这回事） | 零（不需要演，只输出 JSON） |
| 失败影响 | 回复正常 | 数值不变（兜底） |

### 3.2 角色速写（判断器专用的人设摘要）

**不注入完整人设**，而是每张卡准备 100~150 字的"性格速写"。原因：判断"这句话让她怎么感受"需要她的性格，但不需要她的全部设定。

**格式：**

```
【角色速写】角色A：温柔内敛的图书管理员，怕生但渴望亲近。
被夸会害羞低头，被冷落会安静地难过很久。亲密时反应克制，
但一旦放开会很投入。说话轻声，不用感叹号。
```

**为什么必须带速写：**
同一句"抱抱你"——
- 对角色A（温柔内敛）：常规亲昵，欲望 +1
- 对角色B（娇蛮）：可能是挑衅式亲密，欲望 +3

**没有卡，判断器就不知道这个角色怎么感受这句话。**

### 3.3 输入规格

```json
{
  "角色速写": "<100-150字>",
  "当前状态": {"energy": 62, "mood": 45, "desire": 73},
  "场景": {"chat_type": "private", "is_owner": true},
  "对话": [
    {"role": "user", "content": "我今晚想抱着你睡"},
    {"role": "assistant", "content": "……（小声）那你要轻点"}
  ],
  "任务": "判断这段对话让角色的数值怎么变"
}
```

### 3.4 输出规格（严格 JSON，极短）

```json
{"energy": -1, "mood": 2, "desire": 4, "reason": "被亲近请求，开心又害羞"}
```

**约束：**
- 每个字段范围 `-15 ~ +15`
- `desire` 在群聊场景**恒为 0**（不判断、不输出）
- `reason` ≤ 30 字（只给人看，不注入提示词）
- 输出总长度 ≤ 100 token

### 3.5 判断频率与节流

| 场景 | 判断策略 |
|---|---|
| 私聊 | **每条消息都判断**（量小，成本可接受） |
| 群聊（@她 / 明确叫她） | 判断 |
| 群聊（她参与的对话） | 判断 |
| 群聊（与她无关） | **不判断** |
| 防抖窗口内多条消息 | **合并成一次判断** |

### 3.6 兜底

| 情况 | 处理 |
|---|---|
| 判断器超时/报错 | **数值不变**，记日志，不影响回复 |
| 返回非法 JSON | 数值不变 |
| 返回字段越界 | 按边界 clamp |
| 连续失败 3 次 | 该账号本轮跳过判断（保护性熔断 5 分钟） |

### 3.7 成本估算

见 §3.8「三个异步判断器的最终定案」。

### 3.8 【已拍板】三个异步判断器的最终定案

> 我 2026-11-07 拍板。核心原则：**主回复纯净，判断全异步；只有学习用 Pro，其余用 Flash。**

#### 3.8.1 模型分配

| 调用 | 内容 | 模型 | 理由 |
|---|---|---|---|
| **A** | 状态数值 + 画像更新 | **Flash** | 不复杂，Flash 足够；好感度只做 ±5 内调整 |
| **B** | 学习模块（黑话+表达+行为） | **Pro** | 需结合语境推断含义、辨别真伪 |
| **C** | 兴趣点 | **Flash** | 素材已是压缩过的日记/心事/摘要 |
| — | 冲动 | 不碰（已实现） | 现有机制 |

**逻辑：只有"学习"需要 Pro，其余判断都用 Flash。**

#### 3.8.2 调用 A：状态 + 画像（高频）

| 项 | 内容 |
|---|---|
| 判断内容 | 精力 / 心情 / 欲望 + 画像标签/事迹 + 好感度变化 |
| 触发 | **私聊：每条消息**；**群聊：她回复的每条消息**（被 @ 或参与话题时） |
| 模型 | Flash |
| 输入 | 角色速写(150字) + 当前三值 + 相关话题对话 |
| 输出 | 极简 JSON（字段名缩写省 token） |

**⚠️ 两项判断的作用范围不同（我 2026-11-07 精确修正）：**

| 判断项 | 作用范围 |
|---|---|
| **状态数值**（精力/心情/欲望） | **仅对她回复的那一条消息生效** |
| **画像更新**（标签/事迹） | **相关话题里的每个人都做**（不只回复的那条） |

**为什么这样分：**
- 状态是"她自己"的反应 → 只对她实际回应的那一刻有意义
- 画像是"她对这个人的认识" → 话题里任何人说了值得记的事，都该更新

**输出格式：**

```json
{"e":-1,"m":2,"d":4,"p":["部署","夜猫子"],"a":3}
```

字段含义：`e`=精力、`m`=心情、`d`=欲望、`p`=画像标签、`a`=好感度变化

#### 3.8.3 调用 B：学习模块（批量）

| 项 | 内容 |
|---|---|
| 判断内容 | **黑话 + 表达 + 行为**（三者合并为"学习模块"） |
| 触发 | **攒满 20 条对话** |
| 模型 | **Pro** |
| 输入 | 角色速写 + 这 20 条对话 + 已有学习内容（防重复） |
| 输出 | 结构化 JSON |
| 流向 | → `pending` 状态 → **我审批后生效** |

**输出格式：**

```json
{
  "slang": [{"word":"开摆","meaning":"放弃/躺平了"}],
  "reply_to": [{"trigger":"表示赞同","reply":"对味"}],
  "behavior": [{"name":"深夜话少","desc":"凌晨2点后回复变短"}]
}
```

**注意**：行为学习是**角色行为模式**（如"深夜话少""被夸先否认"），**不是**旧 bridge 的 `_learn_auto_reply`（那是探测对方是否开了 QQ 自动回复，属历史遗留，与此无关）。

#### 3.8.4 调用 C：兴趣点（每日一次）

| 项 | 内容 |
|---|---|
| 判断内容 | 我对什么感兴趣（accuracy / valence / strength 三字段） |
| 触发 | **每天一次**（每卡） |
| 模型 | **Flash** |
| 输入 | **当天**的日记 + **当天**的心事 + **当天**的记忆摘要 + 现有兴趣点列表 |
| 关键 | **只用当天数据**，不翻历史；**不用原始聊天记录** |

**为什么用日记/心事/摘要而不用原始记录：**
- 原始聊天一天几百条，喂进去太贵
- 日记/心事/摘要已是压缩沉淀，信息密度高
- 它们本身就是"她认为重要的事"，判断更准

**输出格式：**

```json
{"topics":[{"topic":"DSH项目","accuracy":8,"valence":"positive","strength":7}]}
```

#### 3.8.5 成本估算（修正后）

假设私聊日均 200 条：

| 调用 | 次数/天 | 单次 token | 日总 | 模型 |
|---|---|---|---|---|
| A | 200（私聊）+ 群聊少量 | 约 300 | 约 7 万 | **Flash（便宜）** |
| B | 10（20 条一批） | 约 1500 | 约 1.5 万 | Pro |
| C | 3（三卡各一次） | 约 800 | 约 0.3 万 | **Flash（便宜）** |

**主要消耗在 A，但用 Flash，实际花费低。**

#### 3.8.6 待确认（不阻塞文档）

| # | 事项 | 我的建议 |
|---|---|---|
| 1 | 调用 A 群聊是否也判断"别人说话她没回"的消息 | 建议**只判断她回复了的** |
| 2 | 调用 B 的"20 条"是消息条数还是对话轮次 | 建议**消息条数** |

## 4. 主回复注入预算（防质量下降的核心）

### 4.1 硬规则

| 内容 | 字数上限 | 优先级 |
|---|---|---|
| 人设 | **不限** | 最高（不可压缩） |
| 数值演出指令 | **≤ 60 字** | 可压缩 |
| 行为约束（发言节制） | **≤ 60 字** | 可压缩 |

**总注入 ≤ 120 字**（人设除外）。

### 4.2 只注入"演出结果"，不注入"数值规则"

```
❌ 禁止：
【心情值】当前 45/100，每小时向 50 回归，公式为 (50-x)*0.0561...
【欲望值】当前 73/100，70 以上允许主动...

✅ 正确：
【此刻】有点闷，说话懒一点。
```

**数值公式全部留在数值引擎里，主回复只看结果。**

### 4.3 分层注入

|---|---|---|

| 私聊日常 | 精力 + 心情 + 欲望倾向 | 50 |

| 欲望 < 70 | **完全不提性相关** | 0 |

### 4.4 压场指令（每次必带，放最后）

> 先演好她，再考虑状态。状态是给你的提示，不是你要报告的内容。

## 6. 生活时间轴

### 6.1 定位（关键，别搞混）

| | 生活时间轴 | 心事簿 | 空间 |
|---|---|---|---|
| 是什么 | **她编的日子**，过去时 | **她心里挂着的事**，现在时 | 对外发布的动态 |
| 是否真实 | 虚构（她自己想象） | 由真实事件产生 | 对外公开 |
| 是否消耗 | 不消耗，只是记录 | 说出来后消解 | 发布即消耗 |
| 是否驱动行为 | **不驱动** | 驱动 proactive | 不驱动 |
| 归属 | persona_id | persona_id | persona_id |

**时间轴 = 她的私人生活记录，纯展示 + 供语境，不参与任何决策。**

### 6.2 生成机制：事件驱动 + 空档提醒

**核心原则：不实时编，不强制补。**

```
① 事件触发写入（不编，是记录）
   她看了视频、被戳、冒出念头 → 顺手写一条

② 空档提醒（不是强制补写）
   检测到超过 N 小时没记录 → 提醒她："你有段时间没记了"
   她自己决定：补几条，或者说"那会儿在睡觉"，或者不理会
```

**明确不做的事：**
- ❌ 不列活动清单（清单会让模型逐条选，变成打勾模板）
- ❌ 不强制补写
- ❌ 不实时定时生成

### 6.3 空档检测参数

| 参数 | 值 | 说明 |
|---|---|---|
| 检测间隔 | 每 1 小时 | 后台轻量检查 |
| 触发阈值 | 空档 > **4 小时** | 超过才提醒 |
| 夜间（00:00-08:00） | **也提醒，但尊重她睡觉** | 不强制，她可以回"在睡觉" |
| 补写条数 | 3~5 条（她自己定） | 覆盖空档时段 |

**提醒话术模板（注入给她的提示词）：**

```
你已经 5 个小时没有记录生活了（现在 19:30，上次记录 14:20）。
你可以补写这段时间在干什么，如果那会儿在睡觉或者没什么可记的，
也可以不补。
（如果你想找点东西看，可以随时刷视频挑一个。）
```

**注意最后一句：不是清单，只是顺口一提。**

### 6.4 视频的接入方式（2026-11-09 改定：取消视频池，按需实时刷）

**她说"想看东西"时：**

```
她自然想到"想看点东西"
    ↓ 当下实时搜索视频（搜到的就是此刻最新的）
    ↓ 拉字幕转写 → 模型消化写感想
    ↓ 挑中 1~2 个
    ↓
① 写进时间轴："今晚看了个视频，讲 Transformer 的…"
② 放进心事簿（带标题+链接）
```

**为什么取消视频池**：池子会过期（今天想刷、池子却是一周前补的货，聊起来很假）；
要维持"相对实时"就得一直更新，徒增复杂度；且不需要 B 站账号、实时刷多少条没关系，
所以不需要缓存，**需要的时候当下搜当下刷**。

### 6.5 时间轴与心事的关系（不合表，互相引用）

```
┌──────────────────────┐
│ 生活时间轴（过去时）   │
│ 00:45 趴窗台数外卖车   │
└──────────────────────┘
          ↓ 可以产生（可选）
┌──────────────────────┐
│ 心事簿（现在时）       │
│ source_kind 新增：     │
│  - inner_life（来自生活）│
│  - group（来自群聊）    │
│  - bili（来自视频）     │
│  - diary / qzone ...   │
└──────────────────────┘
          ↓ 驱动
┌──────────────────────┐
│ proactive 主动开口     │
└──────────────────────┘
```

**为什么不合并（三条硬理由）：**

1. **时间性质冲突**：时间轴是她"演出来的过去"，心事是"真实发生的此刻"。混在一起，读者分不清哪些是她编的——**"十点买菜，十点零一分来了心事"这种怪感就来自这里**。
2. **生命周期相反**：时间轴是记录（永不消耗），心事是待办（说出来就消解）。
3. **前端展示需要不同的排版**：一个是有画面感的散文，一个是事件摘要。

**但允许互相引用**：心事加 `source_kind=inner_life`，表示这条心事由她的生活片段引发。

### 6.6 数据流完整性

| 触发 | 写入时间轴 | 产生心事 | 说明 |
|---|---|---|---|
| 空档提醒补写 | ✅ | ❌ | 纯过日子 |
| 她看视频 | ✅ | ✅（带标题链接） | 两者都写 |
| 群里有趣的事 | ❌ | ✅（source=group） | 只进心事 |
| 她突然的念头 | ✅ | 可选 | 看她自己 |

## 7. 视频消费（按需实时刷，2026-11-09 取代原「视频池」）

> **2026-11-09 我拍板：取消视频池（video_pool）。**
> 原因：池子会过期（今天想刷、池子却是一周前补的货，聊起来很假）；要维持"相对实时"
> 就得一直更新，徒增复杂度；不需要 B 站账号、实时刷多少条没关系 → 不缓存，按需实时刷。
> 原「视频池」的 50 条容量 / 补货水位 / 7 天清空 / 供料分离 全部作废。

### 7.1 核心：零定时器 + 事件驱动（我定调）

**避开任何整点、定时任务、固定间隔。** 固定时间/固定间隔去刷或推送，会非常机械、没味道。
她看视频，只因为"那一刻她正好有这个念头"，不是被闹钟叫。

### 7.2 什么时候刷（触发三事件，2026-11-09 已拍板）

| # | 触发事件 | 情境 |
|---|---|---|
| **①** | 她正准备开口找我，但心事簿没有新话头 | 想说话没话说 → 实时搜视频看 → 看完有话头 |
| **②** | 我跟她聊天，话题自然带到了 | 聊到某件事 → 想找视频回应/推荐 |
| **③** | 状态自然落到"想瘫着看点什么" | 精力低 + 心情低 → 那正好看点什么 |

**关键：没有任何一个触发点是"到了几点"或"隔了多久"。** 全是她生活里自然发生的事。

### 7.3 频率与护栏

- **没有固定频率**：可能一天 0 次，可能一天 2 次，跟着念头走，无规律。
- **软护栏**：因为实时搜 + 模型消化会花 token，加一道**当日最多触发 3 次**的软上限，
  防极端情况（某天情绪特别低连续触发）。这不是定时器，不制造规律。

### 7.4 动作链

```
触发三事件之一
    ↓
当下实时搜索（搜到的就是此刻最新的视频）
    ↓
拉字幕转写 → 模型消化写感想
    ↓
挑 1~2 个 → 写时间轴 + 心事簿（带标题+链接）
    ↓
等自然想跟我说话时才分享（不按时间，按念头）
```

### 7.5 分享格式（必须带标题和链接）

**心事里存的内容格式：**

```
<一句感想/评论> 《<视频标题>》 <bilibili链接>
```

**示例：**

```
属下刚才看了个视频，讲 Transformer 是怎么一步步变成智能体的，
还挺有意思。《从 Transformer 到智能体：一次讲透》
https://www.bilibili.com/video/BV1xxxxxxxxx
```

**硬要求：标题 + 链接缺一不可。** 否则我看到分享却找不到原视频。

### 7.6 效果与依赖

| 效果 | 表现 |
|---|---|
| **不尴尬** | 永远聊的是"当下"的视频，不是一个月前的存货 |
| **有生活** | 时间轴偶尔出现"今晚看了个视频……" |
| **不刷屏** | 看完不立刻推；攒成心事，自然开口才分享 |
| **不机械** | 没有规律，只有念头 |

- 触发①依赖 **proactive 完整版**（想念度自然开口，非轮询）先落地。
- 三事件里①②由聊天/主动开口触发，③由状态数值触发，均非定时器。

## 9. 插件拆分方案

按现有插件架构，拆成 **4 个插件**，职责单一：

| 插件 id | 类别 | 职责 | 关键能力 |
|---|---|---|---|
| `persona_status` | model | 三条数值的存储/回归/累积/读取 | tools（查询）、schedules（每小时 tick）、promptSections |
| `status_judge` | model | 异步判断器 | hook（on_reply_ready 后触发异步判断） |
| `life_timeline` | knowledge | 生活时间轴生成与补写 | schedules（每小时检测空档）、tools（写入） |
| ~~`video_pool`~~ | — | **已作废**（2026-11-09 取消视频池） | — |

**依赖关系：**

```
persona_status  ← status_judge（写入数值）
persona_status  ← life_timeline（读数值做语境）
~~video_pool ← life_timeline~~（已作废：视频改按需实时刷，见 §7）
persona_status  ← 主回复注入（需补接 promptSections）
```

### 9.1 为什么这样拆

- **数值**和**判断**分开：判断器可独立调参/关闭，不影响数值存储
- **时间轴**独立：可单独关掉，不影响数值
- **视频消费**按需实时刷：不建池子，挂在事件上（§7），不新增独立插件表

### 9.2 与现有插件的关系

| 现有插件 | 变化 |
|---|---|
| `bili_watch` | **改造**：不再定时刷进池子，改为"三事件触发时按需实时刷"（§7） |
| `poke` | 不变 |
| `repeat_guard` | 不变（保留相似度抑制） |
| `calculator` / `read_file` / `vision_detect` / `auto_reply_detect` / `rp_command` | 不变 |

## 9.3 【关键】插件 vs 改源码 —— 能力边界盘点

> 我 2026-11-06 提出：必须分清哪些能做插件、哪些必须改源码。
> 以下是实测核查结果，**不是推测**。

### 9.3.1 现有插件框架的真实能力（已核实）

| 能力 | 支持 | 接线状态 |
|---|---|---|
| 声明工具（LLM 可调用） | ✅ | 已接线（`registry.tools_for`） |
| `on_message_received` 钩子 | ✅ | 已接线（gateway） |
| `on_notice` 钩子 | ✅ | 已接线（pipeline poke） |
| `on_image` 钩子 | ✅ | 已接线（planner main） |
| `on_command` 钩子 | ✅ | 已接线（pipeline 命令链） |
| `on_reply_ready` 钩子 | ✅ | 已接线（repeat_guard 双跑） |
| `schedules` 定时任务 | ✅ | 已接线（_plugin_schedule_loop） |
| 配置项 `configSchema` | ✅ | 已接线（WebUI） |
| **`promptSections` 提示词注入** | ⚠️ **能声明但没接线** | **manifest 解析了，但代码里无任何消费方 → 注入不生效** |
| `on_send` / `on_persona_load` / `on_memory_write` | ⚠️ **声明了但没接线** | 只在 VALID_HOOKS 白名单里，无人触发 |

**结论：插件框架目前"能做工具、能做定时、能做部分钩子"，但"不能改提示词注入、不能改核心流程"。**

### 9.3.2 逐个功能判断：插件 or 源码

| 功能 | 能做插件吗 | 需要改源码吗 | 说明 |
|---|---|---|---|
| **数值存储/回归/累积** | ✅ 可以 | ❌ 不需要 | 纯计算 + 自己建表（插件可自带表） |
| **数值查询工具** | ✅ 可以 | ❌ 不需要 | 标准 tools 声明 |
| **每小时 tick（回归/累积）** | ✅ 可以 | ❌ 不需要 | `schedules` 已支持 |
| **异步判断器（核心逻辑）** | ✅ 可以（逻辑） | ⚠️ **需要接入点** | 判断逻辑在插件里，但"回复发出后触发"需要钩子；`on_reply_ready` 可用，但它是**同步阻塞**的，异步调用需要改 pipeline 或加新钩子 |
| **角色速写存储** | ✅ 可以 | ❌ 不需要 | 配置项 + 表 |
| **【注入】演出指令进提示词** | ❌ **做不到** | ✅ **必须改源码** | `promptSections` 未接线；且注入位置在 `domain/prompt.py::build_system_prompt`，插件无权干预 |
| **【注入】发言节制指令** | ❌ **做不到** | ✅ **必须改源码** | 同上，属于系统提示词组成部分 |
| **时间轴存储 + 生成** | ✅ 可以 | ❌ 不需要 | 自己建表 + schedules + tools |
| **时间轴空档检测** | ✅ 可以 | ❌ 不需要 | `schedules` |
| **时间轴前端展示** | ⚠️ 部分 | ⚠️ **需要改源码** | 插件能存，但**前端页面需要在 webui 里加路由/组件**，插件无前端渲染能力 |
| **视频消费（按需实时刷）** | ✅ 可以 | ❌ 不需要 | 改造 `bili_watch` 插件：三事件触发时实时搜刷（§7） |
| **心事写入（带标题链接）** | ⚠️ 部分 | ⚠️ 看现状 | 若现有心事写入有现成接口可调则不改；否则要改 repositories |
| **群聊三档配置** | ⚠️ 部分 | ✅ **必须改源码** | 三档判定发生在 `pipeline._evaluate_trigger`，插件钩子 `on_message_received` 在 gateway 阶段，**改不了"要不要回"的决策** |
| **proactive 撒娇模式** | ❌ **做不到** | ✅ **必须改源码** | 主动开口的判定链在 `supervisor._once_proactive`，插件无权干预 |
| **精力影响主动频率** | ❌ **做不到** | ✅ **必须改源码** | 同上 |
| **文爱档行数放宽** | ❌ **做不到** | ✅ **必须改源码** | `max_reply_lines` 在 `pipeline` 里读配置；可以改成读配置项（源码改一处），插件只负责写配置？**不行**，因为要按场景动态切换，必须源码判断 |

### 9.3.3 汇总：必须改源码的 5 处

| # | 文件 | 改动 | 为什么插件做不到 |
|---|---|---|---|
| **S1** | `dsh/domain/prompt.py` | 增加"插件提示词片段注入"入口 | `promptSections` 未接线，注入位置在核心构造流程 |
| **S2** | `dsh/services/planner/supervisor.py` | `_once_proactive` 增加精力/好感四象限判断 + 撒娇模式 | 主动开口判定链在源码里 |

| **S5** | `dsh/services/webui/` | 时间轴/数值面板前端 | 插件无前端渲染能力 |
