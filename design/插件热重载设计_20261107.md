# 插件热重载设计（2026-11-07 我要求）

> **我的原话**：「需要点立即生效，所有东西我们都需要热重载的，就是我们要做的完善一点，像一个成熟的产品，而不是一个破破烂烂需要我们去自适应的玩意儿。」
>
> **要求**：插件管理页点开关 → **立刻生效**，不需要重启服务。
> **定位**：这是「做成成熟产品」的一部分，不是可选优化。

---

## 一、目标

| # | 能力 | 验收标准 |
|---|---|---|
| 1 | 一键开关插件 | 点一下，工具/钩子/定时任务立刻生效或失效 |
| 2 | 改配置立刻生效 | 表单改了参数，下一次回复就用新值，不重启 |
| 3 | 关掉不炸 | 关 A 后，依赖 A 的 B 不会有半残状态 |
| 4 | 开关状态持久化 | 重启服务后，开关状态和配置保持不变 |
| 5 | 失败可恢复 | 热重载失败（如语法错误）不能把服务搞挂 |

### 2.1 注册表本来就有卸载能力

`dsh/plugins/registry.py`：

def provide(self, capability: str, owner_id: str, provider: Any) -> bool:
    # 同一 owner 重复注册同一能力：覆盖（热重载），不叠加   ← 第 26 行注释

def remove_owner(self, owner_id: str) -> int:

**`remove_owner()` 已实现，但全库没有任何调用方。** 这是为热重载预留的钩子。

## 三、缺口清单

| # | 缺口 | 位置 | 影响 |
|---|---|---|---|
| G1 | 运行时开关方法 | `manager.py` | 核心 |
| G2 | **模块缓存未清理** | `manager.py:114-118` | ★ 陷阱 |
| G3 | 依赖检查 | 无人读 `requires` | 关 A 可能让 B 半残 |
| G4 | 开关状态持久化 | 无 | 重启丢失 |
| G5 | 后台任务未纳入管理 | `supervisor` | 已跑起来的任务不会自动停 |
| G6 | 配置热更新 | 无 | 改参数要重启 |
| G7 | `/api/plugins` 路由 | `app.py` | 前端无接口 |
| G8 | 前端插件页 | `dist/index.html` | 无 UI |

### G2 是最隐蔽的坑

`manager._import_module()`：

```python
mod_name = f"dsh_plugin_{plugin_id}"
spec = importlib.util.spec_from_file_location(mod_name, main_py)
module = importlib.util.module_from_spec(spec)
sys.modules[mod_name] = module        # ← 写进 sys.modules
spec.loader.exec_module(module)
```

**问题**：模块对象一直留在 `sys.modules` 里。热重载时如果直接重新 import，Python 可能复用旧模块对象，**改了代码也不生效**。

**必须**：卸载时 `del sys.modules[mod_name]`，重新加载才会真正执行新代码。

## 四、设计方案

### 4.1 核心流程

```
【关闭插件】
  1. 依赖检查：谁 requires 我？
       ├─ 有依赖者 → 拒绝关闭，提示「B 依赖 A，请先关 B」
       └─ 无依赖者 → 继续
  2. registry.remove_owner(plugin_id)     ← 清能力/工具/钩子/定时任务
  3. 停掉该插件的后台任务（若有）
  4. del sys.modules["dsh_plugin_xxx"]    ← 清模块缓存（关键）
  5. info.enabled = False
  6. 持久化开关状态

【开启插件】
  1. 依赖检查：我 requires 的插件都启用了吗？
       ├─ 有未启用的 → 拒绝开启，提示「需先启用 A」
       └─ 都启用 → 继续
  2. _import_module() 重新导入（此时 sys.modules 已清）
  3. 注册能力到 registry
  4. 启动该插件的后台任务（若有）
  5. info.enabled = True
  6. 持久化开关状态
```

### 4.2 失败处理（成熟产品的关键）

| 场景 | 处理 |
|---|---|
| 新代码有语法错误 | **保持关闭**，记 `problems`，前端显示红色「加载失败：具体原因」，**服务不受影响** |
| 依赖缺失 | 拒绝操作 + 明确提示缺谁 |
| 卸载过程中抛异常 | 捕获，记日志，标记该插件「状态异常」，**不让异常冒到请求层** |
| 热重载后功能异常 | 保留「回滚到上次可用版本」的能力（可后续做） |

**原则：插件是插件，插件烂了不能把宿主搞挂。**

### 4.3 依赖冲突处理（待我拍板）

| 方案 | 行为 | 优劣 |
|---|---|---|
| **A 拒绝（推荐）** | 关 A 时有 B 依赖 → 拒绝，提示先关 B | 最安全，无半残状态 |
| B 级联关闭 | 自动把 B 也关掉 | 省事但可能误伤 |
| C 允许 + 警告 | 关 A，B 标记为依赖缺失不加载 | 灵活但状态复杂 |

### 4.4 配置热更新

插件配置（`configSchema` 定义的参数）改完应立刻生效。

**实现要点**：
- 配置存在哪？→ 需确认现有插件配置的存储位置
- 改了之后，插件如何感知？→ 两种做法：
  - **每次读配置**（简单，但要看插件实现）
  - **主动通知插件**（需插件实现 `on_config_change` 钩子）

**建议**：先看现有插件怎么读配置，再定方案。若插件都是「每次用到时读」，那改完自然生效。

## 五、【已拍板】我的决定（2026-11-07 夜）

> 以下是我逐条确认的结果，**不再讨论**。

### 5.1 ★ 最高原则（我的原话提炼）

> **「所有的会直接影响到我们主服务的东西，那都肯定是要最严谨、最谨慎态度和方案。」**

**这条不是只针对工具重名，是通用原则。** 以后所有涉及主服务稳定性、可用性、数据安全的决策，一律按最严谨方案走，不图省事。

**同时我明确**：
> 「代码这方面我真的不懂，我只能说提供设计上的一些思路，敲定设计方向。但是像这种代码维护相关的，你按照成熟产品的标准来就行。」

→ **代码实现层面的事，按成熟产品标准自行决定，不用逐条问；只把设计方向拿给我拍板。**

### 5.2 依赖冲突处理：级联关闭 + 明确提示

**定案**：假设 A 依赖 B，关闭 B 时——

```
点关闭 B
  ↓
检测到 A 依赖 B
  ↓
弹出明确提示：「关闭 B 会一并关闭 A」
  ↓
┌─────────────┬─────────────┐
│   确定       │    取消     │
│  → 一并关闭  │  → 什么都不动 │
│    A 和 B    │             │
└─────────────┴─────────────┘
```

| 操作 | 结果 |
|---|---|
| **点确定** | B 和依它的 A **一并关闭** |
| **点取消** | **什么都不动**，B 保持启用，A 保持启用 |

**要点：**
- 提示必须**说清会关掉谁**（"会一并关闭：A"）
- 依赖链要**传递**：A←B←C，关 C 要提示会关 A、B
- **不允许"只关自己"选项**（我选择级联，不留半残状态）

### 5.3 热重载失败处理

| 项 | 定案 |
|---|---|
| 插件状态 | **保持关闭**（不回滚旧版本） |
| 服务影响 | **完全不受影响**，其他插件照常跑 |
| 错误信息 | **必须到行号**（如 `SyntaxError: invalid syntax (line 42)`） |
| **强提醒** | ★ **插件管理页面必须有明确醒目的错误提示**，不能只写日志 |

**强提醒的具体要求：**
- 插件列表里该插件显示**红色错误状态**
- 鼠标悬停/点开能看到**完整错误原因**
- 不能是"静默失败"——我必须一眼看到"这个插件坏了，原因是 XXX"

### 5.4 插件出 bug 的处理

**我的原话**：「如果插件出 bug，那就考虑功能关闭，就直接不可用，显示错误，并且给到具体的错误信息。」

| 情况 | 处理 |
|---|---|
| 加载失败（语法/依赖/初始化） | **功能关闭、不可用**，显示具体错误 |
| 运行时报错 | 该次调用失败，记日志；**连续失败达阈值 → 自动关闭该插件并强提醒** |
| 插件状态异常 | 页面红色显示，给出错误原因 |

**原则：宁可不工作，也不能半残或静默出错。**

### 5.5 工具重名冲突：拒绝加载

**定案**：**检测到工具重名 → 拒绝加载该插件 + 明确提示冲突对象。**

**理由（我的原话）**：
> 「不是因为之前遇到过所以拒绝，而是所有的会直接影响到我们主服务的东西，那都肯定是要最严谨、最谨慎态度和方案。」

→ 工具重名会导致 API 400，**直接让主服务（私聊/群聊回复）全部失效**，属于最高危级别，必须最严格拦截。

**扩展要求**：凡是可能影响主服务的能力注册（工具、钩子、定时任务），注册前都要做冲突检查，不能等到线上炸了才发现。

## 七、边界提醒

**热重载 ≠ 热部署**。以下不在本次范围：

- ❌ 改 `dsh/` 核心代码后热生效（那要重启服务，正常）
- ❌ 新增插件目录后自动发现（可后续做，扫描目录即可）
- ✅ 本方案只解决：**已加载的插件，开关和配置的热生效**

**这也是一种成熟**：成熟产品会明确边界，不会假装什么都能热更。
