## 2. 设计原则（先于实现，不可动摇）

### 2.1 候选必须多，「挑」才有意义

> 我：「我的看法相反，反而放开，给到 5 条旧账，这样应该更加不容易被当作全说，
> 还是得靠模型自觉，不然失去了「挑选一个想聊的」这个意义。」

**候选越多，挑才成立。给 1 条不叫挑，叫念。**
→ 召回 **3 → 5 条**，一次只准说一件，靠人设自觉 + prompt 强化，**不靠机制硬压**。

### 2.2 遗忘 = 降权，绝不是删除

> 我：「她到底忘没忘只是一个标记的事，数据本身一直在。」

→ 忘掉的心事转 `dormant`（**保留原文**），随时可被唤醒/翻回。**零信息损失。**

### 2.3 惩罚绝不落好感度

`affection_history` 记的是**「她对我的感情」**。扣它 = 让我承受关系降温。
→ **永远不因她的失误扣好感。** 失分是**另一个账本**。

### 2.4 机械记账，人设给重

机制只做三件**通用**的事：**记账、比对、可见**。
「这个惩罚有多疼」由**角色卡文本**决定。
→ 内部字段中性（`dereliction`），**渲染措辞随卡**。

### 2.5 账本在，但不主动念（防 PUA 护栏）

**失分只在「被问到却答不上来」时结算，系统绝不主动播报。**
> 这条是记账与 PUA 的分界线，实现时不得以「提效」为由破坏。

### 2.6 心情 ≠ 好感（关键拆分）

| 概念 | 记什么 | 时长 | 谁驱动 |
|---|---|---|---|
| **好感度** `affection_history` | 她对我的感情 | 累积持久 | `mood_change`（现有） |
| **心情** `mood_state`（新增） | 她当下的状态 | **30 分钟衰减** | LLM 自起标签（见 §4） |

**好感是「对你的感情」，心情是「她此刻的状态」。** 两者分开存、分开算、分开用。

### 2.7 任何机制必须有可感知的出口（新增原则）

> **我**：「我倾向先不要……但是这个效果很难验证。
> 甚至我觉得大多数时候，除了记得自己写过这么个东西，都实际感受不到有这么个事。」

**判据**：关掉这个功能，我能不能感觉到区别？
**感觉不到 → 不做。**

「表里有值」不算验收——这正是铁律 §1.4「测试全绿 ≠ 系统能用」的延伸。

> **本条直接决定了 θ 写入门槛被砍掉**（见 §4.1）：θ 从 0.275 调到 0.825，
> 因为我们的 summary/peek 本来就不产垃圾记忆，表里可能一条都不差。**

## 3. 核心机制：艾宾浩斯三量模型

### 3.1 三量

| 量 | 字段 | 含义 | 落盘? |
|---|---|---|---|
| 重要性 | `importance` | 0~10（现有量表），内容属性 | ✅ 已有 |
| 稳定度 | `stability` | 单位「天」，存活期尺度 | ➕ 新增 |
| 可提取度 | `retrievability` | `R = exp(−t / S)` | ❌ 派生不落盘 |

### 3.2 四档位（沿用现有 0~10 importance）

| 档位 | importance | 初始 stability |
|---|---|---|
| trivial | 0~2 | 0.5 天 |
| normal | 3~5 | 3 天 |
| important | 6~8 | 14 天 |
| critical | 9~10 | 60 天 |

> **旧数据不回填**（决策 #3）：`stability` 为 NULL 时按 `importance` 现算初始值，
> 相当于「从今天开始重新计时」。**不追溯历史。**

### 3.3 三层状态机

```
写入 → active ──(S≥30 且 召回≥2)──▶ long（长期记忆）
         │                            │
         │(R<0.20)                    │(R<0.20)
         ▼                            ▼
      dormant ◀──────────────────────┘
         │
         └─(关联唤醒 / 她主动查到)─▶ active
```

| 状态 | 含义 | 可被常规召回 | 说明 |
|---|---|---|---|
| `active` | 活跃 | ✅ | 默认状态 |
| `long` | 长期记忆 | ✅（衰减慢 4 倍） | `S≥30` 且被召回 ≥2 次 |
| `dormant` | 已遗忘（未删） | ❌ | 仅靠关联/主动查询唤醒 |

### 3.3b dormant 复活方式（2026-11-01 定）

**背景**：记忆衰减到 `R<0.20` 转 dormant，**不再进常规召回**（否则又「翻旧账」）。

| 方式 | 做法 | 体验 | 成本 |
|---|---|---|---|
| **甲：主动查询唤醒** | 她调工具查记忆时才可能查到 | 被直接相关话题触发才回来 | 零依赖 |
| **乙：关联唤醒** | 系统算「牙」与「医院」相关，我说医院时自动送进「牙」 | 更自然、更聪明 | 需 embedding |

**结论**：**乙优先**。因 embedding 已定（BGE-M3）且本期做（`MULTI_MODEL_ROUTING.md` 决策 #13），
底座有了就顺手上关联唤醒；**甲作为乙的兜底**（embedding 挂了也能查）。

> 具体体验（乙）：我说「对了，我牙疼」→ 向量相似度命中 dormant 的「下个月要去看牙」
> → 唤醒回 active → 恢复稳定度 → 她自然接话「你不是说下个月要去看牙吗」。

### 3.4 间隔效应（艾宾浩斯精髓）

```python
spacing_gain = exp(1.5 * (1 - R)) - 1   # R=1 时增益恰为 0
g_eff = 0.5 * spacing_gain
S_new = min(S * (1 + g_eff), 365.0)
```

**R=1 时增益必须为 0** —— 刚记下就重复不该涨；越接近遗忘时想起来，涨得越多。

> ⚠️ 这是 `dsh-memory-hybrid` 明确记下的坑：写成 `1 + (1-R)` 会让密集重复拿到 2 倍增益，**是错的**。

## 4. 心情系统

### 4.1 核心取舍：**砍掉 θ 写入门槛**

> **我**：「大多数时候，除了记得自己写过这么个东西，都实际感受不到有这么个事。」

**判据（新增原则，见 §2.7）：关掉它，我能不能感觉到区别？**
感觉不到 → 不做。θ 从 0.275 调到 0.825，因为我们的 summary/peek 本来就不产垃圾记忆，
**表里可能一条都不差**。这是装饰，不是功能。

→ **心情不影响「记不记得住」，只影响「怎么说话」。**

### 4.2 心情的表达方式：LLM 自起标签 + 强度（不用固定 V/A 坐标）

> **我**：「心情有不同的维度，郁闷和伤心是不一样的；这个我很难给出定值；
> 事实上，这方面我还是建议给 LLM 自己判断。」

**为什么不沿用 V/A 二维数值**：「郁闷」和「伤心」在 V/A 上可能都是
「负效价 + 低唤醒」，但它们是**两种完全不同的感受**。二维数值装不下这个差别。

**改用标签制**：

```json
{"mood": "郁闷", "intensity": 2, "reason": "发现自己忘了一件事"}
```

| 项 | 谁决定 | 说明 |
|---|---|---|
| **心情名字** | **LLM 自起** | 「郁闷」「失落」「雀跃」「心不在焉」「火大」……不预设词表 |
| **强度** | LLM 给 1~3 档 | 1=轻微、2=明显、3=强烈 |
| **怎么影响语气** | **角色卡文本**决定 | 小吉低落时是咬着牙硬撑还是蔫下去，由人设决定 |
| **数值化** | 内部映射 V/A **仅用于衰减计算** | 这个数字她看不见，我也不需要关心 |

**三个好处**：
1. **维度不受限**——LLM 说是「委屈」就是「委屈」，不用硬塞进二维坐标
2. **可感知**——标签直接注入 prompt，语气变化当场听得出
3. **符合我原则**——不给固定值，交给她自己判断

### 4.3 心情如何影响语气（这是它唯一的价值所在）

注入 prompt：

```
【当前心情】郁闷（强度 2）——因发现自己忘了一件本该记住的事
表现为：语气偏沉，句子短，不主动起话头，少用♪，但不必刻意说明原因。
```

**这正是好感度干不了的事**：

| | 好感度 | 心情 |
|---|---|---|
| 时间尺度 | 周/月，慢 | **30 分钟，快** |
| 起因 | 长期相处 | **刚刚发生了什么** |
| 恢复 | 慢慢积累 | **自然漂回中性** |
| 表达 | 关系温度 | **这一刻的劲头** |

同一个好感 100 的小吉，**雀跃时**和**郁闷时**说话是两种感觉——差别当场能听出来。

### 4.4 心情怎么衰减

**30 分钟有效期**：超过就向中性漂移（强度递减至 0）。
不做持久累积——它是**状态**，不是**账本**。

### 4.5 存在哪（**必须按 persona 独立**）

新表 `mood_state`：

| 列 | 说明 |
|---|---|
| `persona_id` | **主键维度**（角色卡） |
| `label` | LLM 起的心情名（如「郁闷」） |
| `intensity` | 1~3 |
| `reason` | LLM 给的原因 |
| `mood_at` | 最后更新时间 |

> ⚠️ **绝不可像好感度那样复制给多张卡**（见 §11）。
> 小吉开心、角色A也跟着开心，那就毫无意义。

## 5. 弃忘台账（账本腿）

### 5.1 数据层：复用 `memory_summaries`

| 字段 | 弃忘时的值 |
|---|---|
| `kind` | `'pending'` 不变 |
| `resolved_at` | 放弃时刻 |
| `resolve_reason` | **`'self_abandoned'`**（新增列） |
| `summary_text` / `keywords` | **完整保留**（比对要用） |

> ⚠️ `memory_summaries` 当前**没有** `resolve_reason` 列。落地时新增该列（推荐）。

### 5.1b 开口即销（已敲定）

> **我**：「开口即销」（resolve only the spoken item）—— 她主动说出口的那一条才算销，
> 没说出口的继续留在候选池。**不是「念 3 条全销」**（缺陷 B 的根因）。

**行为规则**：
1. 每次从 5 条候选中**只挑一件**说
2. **只销她真正说出口的那一条**（`resolve_reason='spoken'` 或 `self_abandoned`）
3. 其余候选**保持未销**，下次继续参与挑选
4. 她**没说出口就自己放弃**的 → `resolve_reason='self_abandoned'`（进入弃忘台账）

### 5.2 结算层：新表 `dereliction_events`

> **先澄清「失分」语义（2026-11-01 我重新确认过）**：
> 讨论中途插入了好感度大改，导致「失分扣在哪」一度聊乱。最终明确——
> **失分扣的是本账本（`dereliction_events`）的分，不碰好感、不碰心情。**
> 三本账彻底分开：
>
> | 账本 | 记什么 | 会因她失误扣吗 |
> |---|---|---|
> | `affection_history` 好感 | 她对我的感情 | **绝不** |
> | `mood_state` 心情 | 她当下状态（30分钟） | 会（标签变「郁闷」，漂回） |
> | `dereliction_events` 台账 | 她「该记住却放手」的次数 | **会，扣的是这本账的分** |

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `persona_id` | 角色卡（第一维度，跨卡通用） |
| `bot_uin` | 溯源账号 |
| `memory_id` | 关联被放弃的心事 |
| `delta` | **正=加分，负=失分**（一本账两面） |
| `reason` | `forgot_after_abandon` / `praised` / `useful_recall` / `self_rescued` |
| `detected_at` | 结算时刻 |
| `trigger_msg_id` | 哪条消息触发 |
| `note` | 依据摘要 |

**总分 = `SUM(delta)`**，按 `persona_id` 聚合。

### 5.3 加减分表（决策 #1：必须有赏）

| 她的行为 | delta | reason |
|---|---|---|
| 主动放手一件事 | 0 | —（只是标记，不奖不罚） |
| **查工具比对到「这是自己放手的」** | **−1** | `forgot_after_abandon` |
| 其中：**当场承认并补救** | −0.5 | 同上（减半） |
| 她提起旧事，**我明确夸奖**（"你还记着"） | **+1** | `praised` |
| 她提起的事**对我有用**（对话顺着聊开） | **+1** | `useful_recall` |
| 她**主动发现自己忘过、并补救** | **+2** | `self_rescued` |

> **赏罚同一本账，正负相抵。** 这不是「惩罚记录」，是「她有多上心」的记录。

### 5.4 判定：只认「查了并比对到」（决策 #5）

**不猜、不推断、不冤枉。** 流程：

```
我说了什么
   ↓
她调用记忆查询工具（现有 query_cognitive，或新增 query_abandoned）
   ↓
工具返回命中一条 resolved_at 有值 + resolve_reason='self_abandoned'
   ↓
工具在这次返回里标记：「⚠ 这条是你自己放手过的」
   ↓
系统看到标记 → 记 delta=-1
```

**优点**：确定性，无猜测。**缺点**：她不查就躲过去了——但**不查本身就是一种答案**。

### 5.5 恢复：分数不能只升不降

| 通道 | 效果 |
|---|---|
| 时间衰减 | 每 30 天历史失分自然 +1（向 0 靠） |
| 主动补救 | 事后自己想起并提起 → 抵消 |
| **我宽恕** | 我说"这次算了" → **该笔清零** |

第三通道把决定权留给你。**她能自由忘，但能不能被原谅是另一回事。**

### 5.6 呈现：常驻但不播报（护栏）

私聊上下文注入一行：

```
【备忘疏漏】你最近有 3 次「该记住却自己放下了」的记录。
```

- 只在她**放手过且被触发过**时出现
- **不推送、不主动提**
- 具体措辞由角色卡决定：角色B看到「失职记录」，其他卡看「备忘疏漏」

| 账本 | 记什么 | 会因失误扣分吗 |
|---|---|---|
| `affection_history` | 她对我的感情 | **绝不** |

**最坏情况**：她失分很高、心情低落，但**她对我的好感一点没掉**。
惩罚落在她自己身上，不在关系上。

## 6.5 好感度：坐标定义与上限配置

### 6.5.1 绝对坐标 0~100

> **我**：「0-100 是绝对坐标，0 是见到就追着骂，这种近乎仇恨的端点，
> 100 就是投怀送抱百依百顺这样的端点（不是绝对的，我只是举个例子，
> 就是，两级确定，上下限自行设置，默认值 50，按照普通网友处理）」

| 值 | 含义 | 表现 |
|---|---|---|
| **0** | 极端负向 | 近乎仇恨，见到就追着骂 |
| **50** | **默认值** | 按普通网友处理 |
| **100** | 极端正向 | 投怀送抱、百依百顺 |

**0 和 100 是确定的两个端点。**

### 6.5.1b 八档（2026-11-01 重写，替代五档）

端点**向下包含**（含下端、不含上端），100 落最高档：

| 区间 | 档名 | 表现 |
|---|---|---|
| `[95, 100]` | 极致偏爱 | 近乎痴迷的偏袒，无条件站在对方那边 |
| `[85, 95)` | 极度信任 | 极度信任与偏爱，非常热络、亲近、毫无保留 |
| `[70, 85)` | 相当亲近 | 熟络度高，愿意主动分享和多聊 |
| `[50, 70)` | 自然随和 | 当普通朋友交流（50 默认值落这档） |
| `[30, 50)` | 客套礼貌 | 保持社交距离感 |
| `[15, 30)` | 明显疏远 | 回复简短，不愿多说 |
| `[5, 15)` | 厌恶 | 冷淡刻薄，能不理就不理 |
| `[0, 5)` | 近乎仇恨 | 一开口就带着刺，随时准备翻脸 |

> 理由：原五档 `<30` 全挤成「稍显冷淡」，0 和 29 无法区分；两端必须拉开。
> 已在 `dsh/domain/affection.py` 落地（`AFFECTION_TIERS`），prompt 不再给具体数字，
> 只给「好感很高（极度信任）+ 表现建议」，数字只在 WebUI 给我看。

### 6.5.1c 单次变化缩放（0.05）

> **我**：「没人会因为对方连着说对 50 句话就投怀送抱……0~1000 更细」
> → 讨论后**保留 0~100，加缩放系数**：LLM 仍输出整数 ±5，系统乘 `0.05`。

| 强度（LLM 给） | 实际变化 | 从 50 到 90 需要 |
|---|---|---|
| +1 | +0.05 | 800 次 |
| +3 | +0.15 | 267 次 |
| +5 | +0.25 | 160 次 |

按平均 +3、每天 5 次互动 ≈ **53 天到上限**（像真人）。
精度改 **2 位小数**（否则 +0.15 会被 round 成 +0.2 而失真）。

> **我补充（2026-11-01）**：单次变化是 **−0.25 ~ +0.25**（不是「只涨」），
> 且**可以取 0**（态度不变时 LLM 给 0 即可，`MOOD:0` 或干脆不出 MOOD）。

### 6.5.2 上下限可配置（架构层）

**架构上永远是 0~100 的绝对坐标，但「允许达到的范围」可配置。**

| 配置项 | 说明 |
|---|---|
| `affection.min` | 下限，默认 0 |
| `affection.max` | 上限，默认 100 |
| `affection.owner_max` | **我自己的上限**，默认 100（不受限） |
| `affection.others_max` | **其他人的上限**，默认 100 |
| `affection.delta_scale` | 缩放系数，默认 0.05（决策 #14） |

**语义**：`clamp(score, min, min(max, 该用户适用的 max))`

### 6.5.3 本服务器的实际配置

> **我**：「除了我以外的好感统一调回 50 从头练，并且加入其他人的好感上限限制……
> 我自己机子这边暂时给其他人采取，上限 90」

| 对象 | 上限 | 说明 |
|---|---|---|
| **我（10000）** | **100** | 全开 |
| **其他人** | **90** | 留一截，不给满 |

> **这是配置，不是架构。** 别人 clone 这个项目，默认是 100/100；
> 这台服务器配成 100/90。**「上限」本身是一种态度表达。**

### 6.5.4 一次性重置（2026-11-01 执行）

| 动作 | 范围 | 目标值 |
|---|---|---|
| 好感重置 | **除我外的所有人** | **统一 50** |
| 历史记录 | 每人写一条 `delta = 50 - 原值` | `source_kind='manual_reset'` |

> **为什么要写历史记录**：不写的话，以后翻 `affection_history` 会发现
> 「怎么突然少了 50 分，谁干的？」——查不出来。
> 铁律要求「派生数据必须自带来源」，这就是落地。

## 6.6 【BUG】好感度跨卡复制

### 6.6.1 现象（2026-11-01 实测）

```
baiwei  user=10000  aff=100.0
jibril  user=10000  aff=100.0     ← 完全相同
baiwei  user=3638414991 aff=97.5
jibril  user=3638414991 aff=97.5     ← 完全相同
baiwei  user=2468985997 aff=91.9
jibril  user=2468985997 aff=91.9     ← 完全相同
```

迁移历史也是成对出现（同一时刻、同一 delta）：

```
#2276 [16:51] baiwei  auto_group_1_explicit_3
#4137 [16:51] jibril  auto_group_1_explicit_3
```

### 6.6.2 性质

**迁移时把同一份好感数据复制给了两张卡。** 不是「两张卡各自的关系」，
是**同一份数据贴了两遍**。

> **我**：「显然是以前没发现的 bug；得修，好感度也是得按照角色卡分开的」

### 6.6.3 为什么要修

虽然目前都封顶 100 看不出影响，但**结构是错的**：
- 小吉和角色A对同一个人的好感应该**可以不同**
- 现在改一个等于改两个，等于**两张卡共用一个感情**

### 6.6.4 修复方向

`user_profiles` 的主键语义应是 `(persona_id, user_id)`，`bot_uin` 只是溯源。
当前 `persona_id` 已经是列，需确认**唯一约束是否含 persona_id**，若不含则补上。

> ⚠️ 修复涉及数据迁移，**必须先出清单给我确认**（哪些行会被拆、拆成什么值）。

## 10. 好处分度设计（跨卡通用）

> **我**：「这个不具有普遍性，我们的机制应该对所有角色卡通用生效；
> 这个我做不好，我只知道模型训练的相关科普视频全都是直接用「分」来表示」

**机制只做通用的三件事，情绪重量由人设决定**：

| 层 | 内容 | 通用性 |
|---|---|---|
| **记账层** | `dereliction_events.delta` 数字 | ✅ 完全通用 |
| **呈现层** | 数字 + 中性措辞（「备忘疏漏」） | ✅ 完全通用 |
| **感受层** | **角色卡文本决定有多疼** | ❌ 不通用，也不该通用 |

对角色B，「作为附属物失职」这句本身够疼；对别的卡，可能就是「有点不靠谱」。
**同一套机制，不同人设自动产生不同的惩罚强度。**
