# 一个以「角色卡」为核心的 QQ Bot

> **这是一个非程序员基于真实使用需求做的设计，不是学术论文。**
>
> 我不是代码从业者，没有系统性地学过编程。这个项目是我花了一个半月，从零搭起来、部署到服务器、每天真实跑着的 QQ 机器人。下面这些文档，是我在做的过程中写下的设计记录。

---

## 一句话说清它是什么

**一个 QQ 机器人框架，但它的核心不是"机器人"，是"角色卡"。**

大多数 QQ Bot 的模型是「一个账号 = 一个机器人 = 一套设定」。这个项目不一样，它用的是**双轴模型**：

```
角色卡（persona）  ×  账号（account）  =  一个会话（chat_stream）
     灵魂                   身体                  具体的对话
```

- **角色卡**是灵魂：人设、记忆、好感、心情、精力、学到的表达习惯
- **账号**是身体：一个 QQ 号，可以挂不同的卡
- **会话**是这两者的乘积：同一个号在不同群/私聊里，可以是不同的角色

这样带来三件事：

1. **一个号可以挂不同的卡**——同一个 QQ 号，在你私聊里是角色 A，在群里是角色 B
2. **一张卡可以换号**——角色 A 今天用这个号，明天换那个号，**记忆和关系跟着卡走，不跟着号走**
3. **卡可以带走**——因为它独立于账号，所以理论上可以导出、拿到别处继续用（详见下面的「愿景」）

这不是为了架构洁癖。这是被真实需求逼出来的：我同时在跑 **3 张角色卡 × 2 个 QQ 号**，如果按"一号一机器人"来做，等于要维护 3 套记忆、3 套关系，而且卡和号焊死在一起，换号就全断。

## 核心架构：四层职责

```
gateway  (8001)  收消息 → 清洗 → 落库 → 透传，不做任何业务决策
planner  (8000)  调度 + 决策 + 分句，禁止直接调 LLM
core     (9000)  Prompt + LLM + 提纯，100% 无状态
webui    (3080)  配置 + 监控 + 查看，不修改业务数据
```

这里有个我认为很关键的判断：**core 是无状态的。**

所有记忆、状态、关系都存在数据库里，每次回复时按需拼进 prompt。这样 core 可以随便重启、随便换模型，而角色的"人生"不会丢。代价是我必须把记忆系统做得非常厚——这就是下面那些记忆相关文档存在的原因。

## 它实际在做什么（不是设想，是已经跑着的）

**回复与感知**

- QQ 群聊/私聊消息回复（支持图片、表情、引用）
- 图片识图：分析图片内容 + 情绪标签 + 判断是不是表情包（md5 去重）
- 文件读取（分页读，处理大文件不爆上下文）
- 联网搜索
- 戳一戳互动
- 群聊三档模式：活跃（概率插话）/ 提名（@或叫名字才应）/ 静默（只回 @）

**角色的"生活"**

- **精力 / 心情 / 欲望**三条数值，0–100，持续变化
- **生活时间轴**：她会自己"过日子"——写下今天做了什么，而不是等你叫她才动
- **按需刷视频**：三个真实触发（想找你但没话头 / 聊天自然聊到 / 状态落到想瘫着看），零定时器，搜到什么看什么，看完写进时间轴
- **定时日记**：每张卡每天 23:00 回顾当天，写一篇

**记忆与关系**

- 摘要（群聊 200 条 / 6 小时，私聊 50 条 / 6 小时，先到先处理）
- **心事簿**：想说但没说的话会被记下来，等合适时机说出来
- 碎片与八卦：群聊里攒的碎片，只允许**群 → 私聊单向流动**，绝不反向说回别的群
- 记忆召回：摘要 / 日记 / 心事三类并列，按权限做向量召回
- 好感度（0–100）
- 兴趣点画像：accuracy / valence / strength 三字段，随时间指数衰减

**学习**

- 表达学习（什么样的上下句接得上）
- 黑话学习（这个群里的词是什么意思）
- 行为学习（对方做了什么 → 她怎么回应）
- 全部异步批处理，不影响主回复速度

**便携性（这条最重要，见下）**

- **酒馆（Tavern）角色卡导入**：上传 V1/V2 JSON，解析人设 + 世界书，生成预览供你确认，再在一个事务里建卡、绑号、留档
- **preset 快照导出**：把一张卡的人设 + 知识 + 选中会话的有效记忆 + 关系数值打包成 JSON

## 愿景：角色卡应该是可以带走的数字资产

这是整个项目最原始的想法，也是我做到现在最在意的一件事。

**现在的痛点是：你在一个平台养熟的角色，换一个平台就死了。** 记忆没了，关系没了，说话方式也没了——它只是那个平台上的一段数据，你带不走。

我想要的是反过来的：

> 今天我在 QQ 上跟她聊了很久，导出这份角色卡。
> 哪天我在别的 Agent 上，把这份东西扔过去，**对方能接着扮演，接着产生新内容。**

不是"导出聊天记录"那种纪念品，是**一份能继续活的资产**：人设、世界书、她学到的东西、她和你之间的关系，全都在里面。

这也是为什么我把角色卡做成独立于账号的一层——**如果卡和号焊死，它就永远带不走。**

我知道这条路只走了一半：导入酒馆卡已经能用，导出 preset 已经能用，但**第三方原生格式的适配和反向会话导入还没做完**（缺对方格式的契约）。这是明确未完成的部分，我没有把它算作已完成。

## 在讲设计之前，先说我是谁

我不是程序员。这不是谦虚，是字面意思——**我一开始连 Agent 是什么都不知道。**

一个多月前，我先是接触了 DeepSeek Harness，然后去试了 Claude Code，再试了 Codex。三个都摸了一遍，才慢慢明白"Agent 能自己动手改东西"这件事到底意味着什么。

坦白讲，这一个多月我学到的东西，**关于 AI 怎么用，比关于编程本身多得多**。我学到的核心不是语法，是：

- 怎么把一件模糊的想法拆成 AI 能执行的具体步骤
- 怎么判断它给的结果是对的还是看着像对的
- 怎么在它出错时定位到底是哪一环错了，而不是重来一遍

### 一开始我以为这件事很简单

决定自己动手的时候，理由很不成熟：**我以为这是件简单的事。**

我当时对 QQ Bot 完全没有概念，觉得无非是"收消息、拼上下文、发回去"，几天能搞定。所谓初生牛犊不怕虎，大概就是这样。

真做下去才发现不是。想加一个功能，就得先搞懂它背后牵扯了什么；搞懂了，再加下一个。

做着做着，心态变了——**从"我在省钱"变成"我想把它做出来"**。

而且我发现了一件没预料到的事：在 AI 辅助下，我居然能完成一个有相当规模的工程。这不是"我学会了编程"，我到现在也不敢说自己会写代码。是**我想实现的东西，真的能被实现出来**。

那种感觉很难形容，但确实是愉快的。可能接近一种**掌控感**：这个系统是我设计的，它按我设想的方式运转，出了问题我知道该去哪儿找。

这不是我一开始想要的。我最初只想要一个能聊天的机器人。

这个仓库里的所有设计，都是在这个过程里一边学一边写下来的。所以它的价值可能不在"多精妙"，而在**它是一个非从业者真实走完全程的记录**——包括走错的部分。

### 一笔账

做这个项目一个月，服务器加 API 调用，总共花了**六七百到一千块**。

这里有个容易被误解的地方：我走的是**中转站**，价格大概是官方定价的一折。所以这一千块对应的实际调用量是 **5280M tokens**——折算成官方价，是另外一回事。

写下这个数字，需要一个简短的解释。

它没有任何值得炫耀的地方：**花掉的钱不等于做出来的价值**。但它确实侧面说明了一件事：这不是一个周末玩具的体量。一个只靠几轮对话拼起来的项目，烧不掉这个量级。

而我原本想省的钱，其实根本省不下来——**这个数如果拿去买 token 继续用现成方案，是够的**。所以从纯经济角度，这个决定是亏的。

但如果一开始就算得这么清楚，我大概不会开始。

## 为什么决定现在把它放出来

先说真正的原因，虽然它听起来不够体面。

**我怕它就这么消失掉。**

这个项目只有我一个人知道。它跑在我的服务器上，每天和几十个人说话，但那群人不知道背后有什么，我也不在任何一个技术社区里。如果哪天服务器欠费、硬盘坏了，或者我懒得管它了——**它就等于从来没存在过。**

我不是程序员，没在任何一家技术公司待过，也没做过什么能被别人看见的东西。这大概是我第一次做出一个**有规模的、真的在运行的东西**。我不太想让它只留在我自己的电脑里。

这是第一个原因，而且是最强的那个。

### 第二个原因：闭门造车的危机感

11-17，我刷到一个官方讲多智能体架构的视频。

那套东西面对的是真实生产场景里的项目改动——一个工程师怎么指挥多个智能体并行推 PR、盯构建、合并代码。我做的是对话，不是一回事。

但有些地方确实相像。比如"角色卡作为唯一对外的接口人"和他们的 Router，"多群多流各自独立推进"和他们的多个 Thread——**结构上是通的**。

而我这一个多月，是在完全没有参照的情况下，自己一点点摸到这里的。

那种感觉不太好形容。一方面有点骄傲，像是自己走对了一条没人指的路；另一方面是**慌**——万一我花了这么久，只是在重复别人早已做过的事呢？

**闭门造车最大的风险不是造错，是造得慢还不自知。** 所以我需要把它拿出来，让别人看见，也让别人告诉我哪里不对。

### 第三个原因：环境在收缩

原本是打算等一个"更完善的版本"再发的。等了很久。

变化是：**支撑这类项目的社区底层在这段时间收缩了。** 常见的 QQ 协议端实现（NapCat、SnowLuma 等）相继停止公开下载，用它们搭起来的东西也就失去了公开讨论的基础。

这件事让我意识到两件相反的事：

1. **只分享设计、不分享协议端实现，是这个环境下唯一合理的方式。** 所以这个仓库里只有设计文档，没有协议端代码，也不打算讨论它。
2. **但"因为环境变了所以再等等"是等不完的。** 环境不会变好，只会在某一天让你连想发都发不出来。

所以我先把**设计**发出来。设计本身不依赖任何协议端，它讲的是：一个角色要有哪些维度才算"在生活"、记忆该怎么存、卡和号该怎么解耦。这些跟 QQ 无关，换成别的平台也成立。

## 这个设计是怎么长出来的

它不是一个设计一次成型的系统。**从最初能跑，到现在这个样子，中间经历了四次结构性重构**，每一次都是被上一版的结构性缺陷逼出来的。

### 第一版：能跑就行（10 月上旬）

最开始很简单：**单账号、单角色卡、单进程**。一个 Python 文件，一个 SQLite 文件，回答消息、存聊天记录、定期总结。

这个阶段解决的问题都很具体、很细：

- 时间锚点——历史消息原来只有"3 分钟前"，超过 7 天变成"较早"，时间信息直接丢了。改成绝对时间 + 相对时间双写。
- 发送者标识——原来只给昵称，同名就分不清。改成昵称 + 完整号码。
- 记忆回读的字段错配——Planner 返回 `at`，Core 读的是 `mem["time"]`，导致时间永远显示"过往"。

**这一版的本质是"把 Chat 做得像 Chat"。**

### 第二次：单账号多角色卡 → 双账号三角色卡（10 月中下旬）

能跑之后，下一步就是想要更多角色。于是先做了**单账号多角色卡**——一个号，挂两张不同的卡。

跑通了，胆子就大了：**双账号三角色卡**。

然后就撞墙了。

上了第二个账号之后，才发现问题多得**根本想不到**：哪条数据属于哪个号？记忆该算谁的？同一个人在两个号上说话算不算同一个人？切换角色时哪些状态该跟着走、哪些该留在原地？当时光是"归属"这一件事，就列出了一整张表逐项判断。

也是在这里定下了一条直到现在还在用的原则：

> **同一台手机、同一个 QQ，用的人不同，那就当作不同的"人"对待。物理上无法分割的，才共用。**

这次踩坑的结论很清楚：**问题不在"加账号"这个动作，在于底层的结构根本没为"多"准备过。** 于是才有了下面的重构。

### 第三次重构：拆进程（10 月下旬）

单进程撑不住了。于是拆成四层：gateway / planner / core / webui，各管一段，边界写死——planner 不直接调 LLM，core 保持完全无状态。

这次重构的验收标准，我到现在还记得很清楚，因为它是用一句话定义的：

> **明天加第三个账号，需要改几处代码？—— 0 处。**

这句话比任何架构图都有用。它把"架构好不好"变成了一个可以数出来的数字。为了让这个数字不退回去，测试夹具从这时起**固定放 3 个假账号**——任何"只对两个号成立"的代码，测试会先失败。

### 第四次重构：角色卡升为第一维度（10-31，最关键的一次）

这一版改动最大，因为它动的是**地基**。

原本角色是**写死在代码里**的：「角色 A 在群里，角色 B 在私聊」。听起来没问题，直到出现两个真实故障：

1. **两个角色互相不知道对方在干什么**——同一个人跟 A 说的事，B 完全接不上，因为两条信息链是断的。
2. **换号即断、加卡即改代码**——角色和账号焊死在一起。

真正的转折点是意识到：**我一直在把"角色"当成账号的属性，其实账号才是角色的临时载体。**

于是把角色卡提升为**第一维度**：

```
角色卡（persona）  ×  账号（account）  =  会话（chat_stream）
```

这个改动牵动 schema 迁移、记忆归属、画像、好感、token 记账——几乎全部要回头适配。但它一次性解决了三件事：

- 一个号可以挂不同的卡
- 一张卡可以换号，**记忆和关系跟着卡走，不跟着号走**
- 卡独立于号，所以**理论上可以带走**

**“卡可以带走”这件事，不是后来想到的功能，是第三次重构的直接产物。**

### 之后：往上盖

地基定完之后，才轮到往上加：状态三轴（精力/心情/欲望）、生活时间轴、碎片与升级、心事簿、酒馆导入、preset 导出。这些都是 11 月的事。

顺序很重要——**先有"卡是独立的"，才可能有"卡能带走"。** 反过来不成立。

## 几个具体的设计取舍

**① 碎片怎么变成长期记忆**

群聊里每天说的绝大部分是废话。全存下来会淹没上下文，全丢掉又会漏掉真正重要的东西。

三段式：**碎片（fragment）→ 打分 → 升级**。

- 碎片先**全量落库**，给 3 天 TTL，不预设重要性
- 打分只决定「**是否升级**」，不决定「是否保留」——打低了碎片也还在，只是不升级
- 升级阈值 ≥7 才进入群聊长期记忆；≥8 才会主动私聊开口
- 升级时**推进该群总结游标**（覆盖式），常规摘要循环不会再重复总结同一段

关键在于：**打分不负责删除，只负责升降。** 判断失误的代价是"没升级"，不是"永久丢失"。

**② 心事怎么存**

她不是每句话都说出口的。摘要时**独立判断**「有没有想说没说的」，写进心事簿。

心事有 48 小时 TTL，但消耗它的方式只有一种：**主动私聊开口说出来**。产生量远大于消耗量，所以心事会堆积——这不是 bug，这是设计：一个内向的角色本来就该攒着一些没说出口的话。

**③ 三张卡不串号，又不能全隔离**

解法是按维度拆存储：卡资产带 `character_id`、号资产带 `account_id`、流带三元组，各自独立；再靠权限决定哪些可以被谁读到。

碎片允许**群 → 私聊单向流动**，但绝不把私聊里说的话反向说回别的群。

## 几条我认为最值得分享的设计判断

**1. 不做硬编码的消耗表**

精力怎么掉，不写死一张表，交给模型按角色自己的时间轴判断。写死会立刻穿帮：真实的人不会因为"发了 3 条消息"就固定掉 5 点精力。

**2. 数值是时间轴的输入，不是反过来**

心情低 → 她写下低落的一天。反过来（写了低落的一天 → 心情变低）会形成自激振荡。

**3. 只软过滤，永不物理删除**

记忆有 TTL，但 TTL 只影响"进不进候选池"，记录本身永久留在库里可查。删除不可逆，而角色的过去应该始终可追溯。

**4. 异步判断，主回复零负担**

状态判断、学习、兴趣点分别走三条独立的异步链路，主回复路径上不做任何额外推理。角色的"内心活动"不能拖慢她开口的速度。

**5. 失败就静默，不写兜底文案**

出错时不要输出"抱歉我卡了""系统繁忙"这种话——一眼假，角色当场崩掉。宁可这一轮不说话。

## 关于这份仓库的边界

- 这里是**设计文档**，不是 API 手册，不含可直接运行的代码。
- **不含、也不讨论 QQ 协议端实现。** 那部分依赖社区项目，且当前环境下不应公开传播。

## 参考与致谢

这个项目的起点，是我想在自己电脑上跑一个现成的 QQ Bot。

**MaiBot** 是我最初的选择。它做得比我当时需要的完善得多，自带插件系统（近似创意工坊的形态），意味着完全可以只写一个插件把想要的东西挂上去，而不是另起一个项目。

**我知道那条路更省事，但我没走。**

最开始的理由很单纯，也很不成熟：**它太费 token 了。** 我当时部署的版本，几乎每条回复都要调十几二十次模型，账单先撑不住了。而在我看来，我要的东西并不复杂——**我以为自己能做一个更简单的。**

真做下去才发现想错了。一个 QQ Bot 远不是"按概率回不回 + 拼点上下文"，光"这条消息该不该理"就牵扯到群聊三档、私聊门控、热聊状态、防重复、防串号一大堆东西。

改的过程中我把它的实现读了一遍。模型档位划分（replier / planner / memory / utils / vlm / embedding / learner）直接影响了本仓库 `MULTI_MODEL_ROUTING` 的设计；表达学习那套"高频预筛 + 上下文推断"的链路也来自它和 **astrbot**。

**所以准确地说，这个项目不是从零发明，而是站在一个成熟实现上，往我自己更在意的方向继续做。** 如果本文档里有任何设计看起来眼熟，很可能就是来自他们。

也感谢 [astrbot](https://github.com/AstrBotDevs/AstrBot) 及其插件 `astrbot_plugin_self_learning`。

### 还有一个人：小草

插件系统这件事，最初的动因不是我。

当初是我推荐小草用了 MaiBot 的一键包。他后来发现了一个很具体的使用体验问题——**没法取消回复的引用，也没有相关设置项**。为了这个，他干脆自己去找别的方案。

他最后落到一个社区项目上（那个项目后来据说因为平台方的压力，已经无法下载了），**在那上面写插件，实现了我们想要的效果**。他把做出来的东西在群里展示给我看。

**那一刻我才意识到：原来可以这样。** 后来我决定做自己的插件系统，起点在这里。

我得说清楚，他做的是"用插件补齐一个具体缺口"，我做的是另一套东西，两者规模差得远。但没有他先走那一步，我大概不会想到这条路。

谢谢小草。

## 关于并行调度

最后补一句技术上的取舍。官方那套架构里有 Router + Worker 分层、Worker 池、事件驱动的任务分发。**这些我没有做，也不打算为现在的规模做。**

引入 Worker 池意味着 token 成本翻数倍，而我的用量（三张卡、两个号、若干个群）远没到需要它的程度。我需要的是"一个角色像在过日子"，不是"一个工程师指挥二十个智能体"。

规模决定架构。这一点上我选择不做。
